# 交付说明 — Operation Blackout

一个用 Three.js 写的第一人称射击游戏。目标是对标现代军事射击游戏（Call of Duty）的画面水准。

**当前诚实结论：没有达到那个目标。** 一个独立的严格评审 agent 做了五轮盲测，最新一轮给 5.5/10，并且明确说把它和真实的 MWII/BO6 街景放在一起，仍然能在一秒内认出哪个是真的。但 alley 那一帧它承认「缩略图大小可能会认错」。

## 2. 怎么跑

```bash
cd game
npm install
npm run dev          # http://localhost:5173
```

`npm run build` 出静态包到 `dist/`，`npm run preview` 起服务。

**加载需要 75–145 秒**（取决于机器负载）。这是程序化贴图烘焙的代价，目标预算是 90 秒，目前会超。这一项没解决。

### 验证

```bash
npm run build                    # 构建
node tools/physics.test.mjs      # 物理，必须 26/26
bash tools/oneshot.sh 5000 hero out.png    # 截图，2–5 分钟
```

**重要：`npm run build` 通过不等于游戏能跑。** 我在这上面栽过一次 —— Vite 只打包不执行，一个跨方法的未定义引用（`_updateViewRig` 读了 `update()` 的局部变量）构建完全正常，但首帧就抛异常，`__GAME_READY__` 永远不会置真，所有截图返回加载画面。构建通过之后一定要真的启动一次。

### 工具

`tools/` 下有 20 个脚本，多数是这次做出来的测量工具，不是玩具：

| 工具 | 用途 |
| --- | --- |
| `oneshot.sh <port> <pose> <out>` | 单帧截图。pose：hero / alley / closeup / skyline / goldenHour |
| `multishot.sh` | **一次烘焙出多个变体** —— A/B 对比必须用这个，否则两次烘焙之间会混进别的变化 |
| `soldiershot.sh` | 冻结巡逻中的士兵拍静帧，并渲染一张与画面对齐的材质 ID 图 |
| `matstats.mjs` | 配对画面帧和 ID 图，报告每个材质占多少像素、渲染成什么值 |
| `px.mjs` / `region.mjs` | 亮度探针 |
| `diagshot.sh` | 不截图，只 dump draw call、三角形数、色调映射、泛光、环境光 |
| `?fx=key:value` | URL 参数覆盖后处理参数，不用改代码就能 A/B |

## 3. 真的做好了的部分

这些是有测量数据支撑的，不是感觉。

**光照管线本身是对的。** alley 那一帧的阴影半影在物理上站得住：6 米投影距离对应 16 像素的过渡（206.8 → 116.8），日照/阴影比 0.148，防火梯投下的斑驳光影。评审的原话是「alley 这一帧证明渲染器做得到这件事，剩下的问题是内容和标定，不是架构」。

**接触遮蔽。** 沙袋与地面的交界处有 35 像素的接触带，最深处对恢复后的地面是 4.7:1。沙袋、油桶、护栏都真的坐在地上了。开阔路面的亮度变化在 1% 以内 —— 早期一个版本的宽域 AO 曾经吃掉路面 56% 的亮度，这次没有重蹈。

**画面能到白了。** 五个姿势的世界内容最高值 247/234/249/253/239，高于 200 的像素 0.62% / 3.1% / 1.35% / 10.4%。高光候选点（亮度 >150 且高于自身 17×17 邻域均值 1.6 倍）在四个姿势里有 280–1013 个。

**路面结构。** 相关性衰减到 lag 16 仍有 0.135，且四个恒定深度带里都没有周期性复现 —— 之前的 Voronoi 网格已经彻底消失。

**程序化内容管线。** 一个字节的外部资源都没有。城市、士兵、武器、贴图、音效全部代码生成。

**物理。** 胶囊碰撞 + BVH，26 项测试全过，包括滑铲、翻越、台阶。

## 4. 没做完的部分

按评审给的严重度排。

### 武器视图模型（SEVERE）
占 4/5 姿势里约 25% 的画面，是盲测中第一个暴露的地方。刚做了一轮大改（导轨按 MIL-STD-1913 重建、加了面板接缝、手指改成锥形加烘焙遮蔽），**但这一轮改完之后还没有经过评审**。上一轮的评价是「400 像素不间断的表面，真实画面里不存在这种东西」。

顺带说明一件事：评审说「没有抛壳口、防尘盖、辅助推机柄、抛壳挑板」，实际上这四个从一开始就有，全在 +X 侧面，而 hip 姿势的相机在 −X 侧，所以五个姿势里一个都拍不到。「看不见」成立，「没有」不成立 —— 真枪左侧也确实没有这些。

### ~~goldenHour 这一姿势~~ —— 已修复

原症状：阴影区和日照墙面色相差 **1.8°**（31.0° vs 32.8°），天空在 199°，即地面阴影完全没接到天光。

**真正原因：环境光的半球采样是错的。** 旧的四探针加权平均里有两个探针只在地平线上方 3.4°，却占 32% 的权重；黄金时刻太阳侧地平线亮度是天顶的 25 倍，于是它们拿走了红通道的 78%。所谓「天光」实际上是太阳光 —— 阴影当然和主光同色。换成 6×12 分层的余弦加权半球积分（与 512 采样参考值误差 1% 以内，约 7 ms，每次时间变化算一次）后：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 阴影路面色相 | 31.0 | **201.3** |
| 日照墙面色相 | 32.9 | 35.8 |
| **分离度** | **1.9°** | **165.5°** |

阴影路面现在距天空自身色相只有 2°。同样的反转在其他姿势也出现（skyline 阴影女儿墙 32.2 → 190.9），而所有日照面保持暖色。

顺带修掉的：旧的补光还比真值亮 2.4 倍 —— `HEMI_SHARE` 一直在悄悄补偿这件事。以及太阳正午从 11.6h 调到 11.95h，因为 4.6° 时平地上的 cos(N,L) 只有 0.080，太阳在自己的场景里都不是主光源；这同时消除了阴影相机深度范围被 `max(0.14, sunDir.y)` 截断的问题。

五个姿势高光全部上升（>200 像素 +11% 到 +46%），hero 的直接:间接比从 3.8:1 到 5.2:1，落进 4–8:1 的晴天区间。代价是三个姿势均值下降 4–16%，因为补光现在是正确的、更弱的值。

### ~~砖墙灰缝被压黑~~ —— 已修复

原症状：alley 右侧砖墙 39% 的像素亮度 ≤4，且是**削顶**不是暗，六道灰缝每道都有连续 4–5 条扫描线正好是 0.0，整面墙读作打孔铁板。

原因是我自己引入的：删掉 LUT 的暗部抬升之后又加了对比度。而 `(s - 0.5) * contrast + 0.5` 是绕 0.5 的线性伸长，contrast 1.10 下所有低于 `0.5*(1 - 1/1.10)` ≈ code 12 的值都会算成负数被 clamp，灰缝正好落在这个带里。换成两端保持的形式（在同一轴上变陡，但渐近趋向 0 和 1）：

| 同一测量框 (900,0 380×460) | 修复前 | 修复后 |
| --- | --- | --- |
| 亮度 ≤4 的像素 | **39.0%** | **4.6%** |
| 完全归零 | 大量连续扫描线 | 0.95% |

### 士兵（部分修复）

装甲背心从身体里挪出来了（原来在胸腔胶囊内侧 26 毫米，衬衫直接画在装甲上面），迷彩尺度也修正了（平均色块从 1.2 厘米到 8.7 厘米）。

制服反照率分两次抬到位：初版约 3%（木炭），第一次修到 6%，仍低于实物的 10–18%，在 alley 里比身后的墙暗 8.9 倍、只能读作剪影；第二次抬到约 11%。**现在头盔、护目镜、防弹背心板型、腰包、膝盖、靴子在 alley 里都能分辨出来。**

**但还有一条没解决：士兵没有前臂和手。** alley 里右臂是一个到肘部就截断的圆锥，末端是个钝的圆帽。评审在第五轮提过，当时被其他项盖过去了。这是目前士兵身上最明显的缺陷。

### 其他
- 屋顶高光在沸腾：同一材质同一深度的 160×90 区块内亮度跨 222 级，相邻像素平均跳 12–16 code。运动中会剧烈爬行。假设是 roughness 的 mip 链没做方差过滤，**未验证**。
- 场景道具（板条箱、遮阳篷、市场摊位）还是没贴图的纯色盒子。皮卡是没有车轮的黑色板。
- 远景城市是米色棱柱加深色矩形窗，没有天线、空调外机、水箱。
- 加载时间 75–145 秒，超出 90 秒预算。

## 5. 关于这次的工作方式，值得说明的一点

这次找到并修复了 **23 个不报错的 bug**。它们的共同特征是：不抛异常、构建通过、画面「就是看着有点不对」。举几个有代表性的：

| 现象 | 真正原因 |
| --- | --- |
| 路面像 Worley 噪声 | `onBeforeCompile` 拿到的 shader 里 `#include` 还没展开，三处字符串替换全部没匹配上被静默丢弃 —— 整个地面 shader 从来没运行过 |
| 全画面网格状纹路 | AO 模糊的采样点在 `0, ±2, ±4, ±6, ±8`，从不比较相邻纹素，在半分辨率缓冲自身的奈奎斯特频率上响应**正好是 1.0**，周期 2 的抖动怎么滤都过得去 |
| 道具没有接触阴影 | `GBufferPass` 的 override 材质没做实例化支持，所有 `InstancedMesh` 道具在 G-buffer 里堆在世界原点 —— 道具根本不在缓冲里 |
| 什么曝光都到不了白 | LUT 在 AgX 之后又叠了一层 log2 空间的胶片 S 曲线，显示白被结构性钉在 224 |
| 黄金时刻没有影子 | `dim` 同时乘进了 `sunColor` 和 `sunIntensity`，主光按 `dim²` 缩放 |
| 装备和制服分不开 | 装甲板在胸腔胶囊内侧 26 毫米 |
| 整面墙同一个黑点图案 | 每块墙板都从贴图的**同一个角**取 UV |
| 黄金时刻阴影是橙色的 | 环境光四探针里两个贴着地平线却占 32% 权重，太阳侧地平线拿走红通道 78% —— 「天光」其实是太阳光 |

**这些都不是靠猜找到的，是靠测量。** 而且有一个反复出现的教训：评审 agent 的**视觉判断一直很准，但因果归因错了至少 6 次**。它说接触阴影失效是因为搜索半径塌成 3 像素 —— 实测半径下限要到 66 米才起作用，而沙袋在 6 米；它说网格纹是 alpha test —— 整个 `src/` 里没有一处 `alphaTest`。

后来的做法是：把评审的观察当作**假设**交给负责该文件的 agent，要求它自己测量后再动手，并明确报告哪些说法自己的测量不支持。这之后每一轮都有 3–5 条被推翻，而真正的根因全是负责的 agent 自己测出来的。

**如果要继续做这个项目，建议保留这个流程**：评审负责指出「哪里看着不对」和严重度排序，不要让它的因果假设直接变成工单。
